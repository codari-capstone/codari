# 인증 API — 프론트엔드 제안

> **이 문서는 결정이 아니라 제안이다.** #20(로그인)을 만들면서 `web/src/api/provisional.ts`에 손으로
> 적어 둔 임시 계약을 그대로 옮긴 것이다. 명세(#2)와 인증 API(#24)가 실제 계약을 정한다. 프론트는 이
> 모양으로 화면을 완성해 두었다. 실제 응답이 아래와 다르면 프론트가 맞춘다.
>
> 아래 중 **"꼭 필요한 것"**은 서버만 지킬 수 있거나, 어긋나면 화면이 기능명세(COM-07 등)와 다르게
> 동작하는 부분이다. **"프론트가 추측한 것"**은 서버가 다르게 정해도 되지만, 그러면 각 항목에 적은 곳을
> 프론트가 고쳐야 한다.
>
> 이 파일은 `contracts/openapi.yaml`이 생기기 전까지 쓰는 임시 Markdown 제안서다. 실제 명세가 생기면
> 이 문서는 없어진다. `contracts/problems-list-proposal.md`와 같은 형식이다.

## 요약

| 구분 | 항목 |
| --- | --- |
| 꼭 필요한 것 | 로그인 실패는 이유 구분 없이 401, 세션은 `HttpOnly` 쿠키, 로그인 제한(COM-07)은 서버가 세고 429로 알림 |
| 프론트가 추측한 것 | 비로그인 `GET /api/me`는 401, 로그인 응답 본문에 `AuthUser`, `id`는 숫자·`role`은 `'USER' \| 'ADMIN'`, 오류 본문은 RFC 9457 |
| 아직 만들지 않은 것 | COM-04 토큰 갱신, COM-02 GitHub 로그인 |
| 팀이 정할 것 | 로그인 폼이 '계정 규칙'의 비밀번호 규칙을 검사해야 하는가 |

## 1. 타입

`web/src/api/provisional.ts`에서 그대로 가져왔다.

```ts
type Role = 'USER' | 'ADMIN'

interface AuthUser {
  id: number
  nickname: string
  role: Role
}

interface LoginRequest {
  email: string
  password: string
}
```

## 2. 엔드포인트

경로와 상태 코드는 `web/src/api/provisional.ts`의 `ProvisionalPaths`와 `web/src/features/auth/authQuery.ts`가
부르는 그대로다.

### `GET /api/me`

현재 세션을 묻는다. 요청 본문 없음.

- 로그인 상태: `200`, 본문 `AuthUser`
- 비로그인: `401` (아래 ④ 참고)

### `POST /api/auth/login`

요청: `application/json`, 본문 `LoginRequest` (`{ email, password }`).

- 성공: `200`, 본문 `AuthUser`. 세션 쿠키를 `Set-Cookie`로 심는다 (아래 ② 참고).
- 실패(가입되지 않은 이메일, 비밀번호 불일치): `401` (아래 ① 참고)
- 로그인 제한 중: `429` (아래 ③ 참고)

성공 응답에는 본문이 있어야 한다. `loginRequest`는 본문이 없는 성공 응답을 성공으로 읽지 않고
오류로 올린다 (`authQuery.ts`의 `result.data !== undefined` 검사).

### `POST /api/auth/logout`

요청 본문 없음. 성공: `204`, 본문 없음. 서버는 세션 쿠키를 지운다.

`logoutRequest`는 2xx가 아닌 응답을 오류로 올린다 (`authQuery.ts`의 `response.ok` 검사).

### 오류 본문

오류 응답은 RFC 9457(Problem Details) 모양이다. `web/src/constants/errors.ts`의 `ProblemDetail`이 읽는
필드는 `type`, `title`, `status`, `detail`이고 모두 선택 항목이다.

본문에 `status`가 있는지는 서버가 신경 쓸 필요가 없다. 프론트는 오류를 올릴 때 HTTP 응답의 상태 코드를
`status`로 덮어쓴다 (`web/src/features/auth/authQuery.ts`의 `fail`).

- 본문이 객체이면 그 필드를 그대로 두고 `status`만 HTTP 상태 코드로 바꾼다.
- 본문이 없거나 객체가 아니면 `{ status: HTTP 상태 코드 }`만 올린다.
- 본문의 `status`와 HTTP 상태가 다르면 HTTP 상태가 맞는 것으로 보고 본문의 값은 버린다.

이렇게 한 까닭: `status`가 없는 401에서 화면이 COM-07 문구 대신 일반 문구로 떨어진 일이 있었다. 서버가
지켜야 할 것은 올바른 HTTP 상태 코드뿐이다.

## 3. 꼭 필요한 것 — 이유와 함께

### ① 로그인 실패는 이유를 구분하지 않는다 — 비밀번호가 틀려도, 없는 이메일이어도 똑같이 401

COM-07은 실패 이유와 관계없이 같은 문구를 보여 주라고 정한다. 프론트는 `401`을 그 문구 하나에
연결한다 (`web/src/features/auth/loginSchema.ts`의 `loginErrorMessage`).

**이 구분 없음은 서버만 지킬 수 있다.** 가입되지 않은 이메일에 `404` 같은 다른 코드를 주면 화면에 다른
문구가 뜨고, 그 순간 그 이메일이 가입되어 있는지가 밖으로 새어 나간다. 프론트는 서버가 어떤 코드를
줬는지 보고 문구를 고를 뿐이어서 이것을 막을 수 없다.

- 비밀번호 불일치와 가입되지 않은 이메일은 **같은 상태 코드(401)와 같은 모양의 본문**을 준다.
- 응답 시간이나 헤더로 둘이 구분되지 않게 하는 것은 서버가 알아서 판단할 일이다. 프론트가 확인하는
  것은 상태 코드뿐이다.
- COM-07은 로그인 제한도 가입되지 않은 이메일에 같은 기준으로 걸라고 정한다. 가입되지 않은 이메일도
  가입된 이메일과 같은 기준으로 429가 나와야 한다. **이 부분을 확인하는 프론트 테스트는 없다.**
  서버 테스트에서 확인해 주길 바란다.

### ② 세션은 쿠키다 — `HttpOnly`, `SameSite=Lax` 이상

로그인 성공 시 서버가 세션을 `Set-Cookie`로 심는다.

- `HttpOnly`
- `SameSite=Lax` 또는 `Strict`
- 운영 환경은 `Secure`도 붙이길 권장한다 (프론트가 요구하는 것은 아니다).

프론트는 토큰을 들고 있지 않다. `web/src/api/client.ts`가 `credentials: 'same-origin'`으로 요청을 보내고,
화면과 API가 같은 도메인이라 (개발은 Vite 프록시, 운영은 ALB) 브라우저가 쿠키를 알아서 실어 보낸다.

이유: 토큰을 응답 본문으로 주면 프론트가 자바스크립트 변수나 저장소에 들고 있어야 하고, XSS 한 번이면
읽힌다. `HttpOnly` 쿠키는 자바스크립트가 읽을 수 없다.

### ③ 로그인 제한은 서버가 세고, 429로 알린다

제한이 걸리는 실패 횟수와 제한 시간은 COM-07이 정한다 (`docs/feature-spec.md`). 이 문서에 옮겨 적지
않는다. 그 횟수는 서버가 센다 (백엔드 담당과 정한 사항, PR #87). 제한 중인 로그인 요청에 `429`를 준다. 프론트는 `429`를 COM-07의 제한 문구로 바꿔 보여 줄
뿐이다 (`loginSchema.ts`의 `loginErrorMessage`).

프론트는 실패 횟수를 세지 않는다. 목(`web/src/mocks/handlers.ts`)도 일부러 세지 않는다.

## 4. 프론트가 추측한 것 (서버가 다르게 정해도 되는 부분)

### ④ 비로그인 `GET /api/me`는 401로 가정했다

`200` + `null` 본문도 가능한 계약이다. 401로 건 이유는 "로그인하지 않았다"를 상태 코드로 말하는 쪽이
자연스러워서다.

`web/src/features/auth/authQuery.ts`의 `meQuery`가 401을 `null`(비로그인)로 바꾼다. 서버가 `200` +
`null`로 가면 **이 분기 한 줄이 바뀐다.** `401` 외의 오류(500 등)는 `meQuery`에서는 오류로 올라간다.
하지만 화면이 보는 `useAuth`(`web/src/features/auth/useAuth.ts`)는 그 오류를 내보내지 않고 비로그인으로
다룬다. 따라서 **`/api/me`가 500을 주면 프론트에서는 로그아웃과 구분되지 않고**, 보호된 화면에서는 방문자가
로그인 화면으로 보내진다. 서버의 오류 의미를 정할 때 이 점을 알아 두길 바란다.

### ⑤ 로그인 응답 본문에 `AuthUser`를 담는다고 가정했다

204만 주면 프론트가 로그인 직후 `GET /api/me`를 한 번 더 불러야 한다. 왕복이 하나 늘고, 헤더가 그 응답이
올 때까지 로그인 전 모습으로 한 번 더 그려진다. 본문 없이 가기로 하면 `loginRequest`를 그에 맞게 고치고
성공 뒤 `/api/me`를 다시 부르도록 바꾼다.

### ⑥ `AuthUser.id`는 숫자, `role`은 `'USER' | 'ADMIN'` 두 값

`id`가 문자열(UUID 등)이면 타입을 바꾸면 된다. `role`에 다른 값이 생기면 관리자 메뉴 표시 같은 권한
판단을 하는 곳을 같이 봐야 하므로 미리 알려 주길 바란다.

### ⑦ 오류 본문은 RFC 9457

`web/src/constants/errors.ts`의 `toUserMessage`가 이 모양을 읽는다. `type`이 표에 있으면 그 문구를,
없으면 `status`로 고른 문구를 쓴다. 서버의 `detail`은 사용자에게 보여 주지 않는다. 다른 모양으로 가면
`errors.ts`를 고친다. 다만 로그인 화면의 401·429 문구는 `toUserMessage`를 거치지 않고 `status`만 보고
고르므로 `type`은 영향을 주지 않는다 (`loginSchema.ts`의 `loginErrorMessage`).

## 5. 아직 만들지 않은 것 — 서버가 먼저 정해야 하는 것

### COM-04 토큰 갱신

화면에는 아직 없다. 서버가 정해야 한다.

- 토큰 수명 (접근 토큰과 갱신 토큰이 따로 있다면 각각)
- 갱신 엔드포인트가 무엇을 뜻하는지 (경로, 쿠키만으로 갱신하는지, 응답 본문이 있는지)
- 갱신 실패와 "처음부터 로그인하지 않은 상태"를 프론트가 어떻게 구분하는지. COM-04는 갱신에 실패하면
  로그인 화면으로 보내라고 하는데, 이는 비로그인 `GET /api/me`의 401(④)과 의미가 다르다.

### COM-02 GitHub 로그인

화면에는 아직 없다. 서버가 정해야 한다.

- GitHub OAuth 앱 등록 (누가, 어느 계정으로)
- 리다이렉트 URI (개발·운영 각각)
- 서버 쪽 콜백 처리와, 성공·신규 가입(닉네임 입력) 뒤 프론트로 돌려보내는 방식

## 6. 목이 실제 서버와 다른 점

목은 `web/src/mocks/handlers.ts`와 `web/src/mocks/fixtures/users.ts`에 있다. **목을 명세로 읽지 말길
바란다.** 개발과 테스트용 가짜 응답이고, 실제 서버와 다른 곳이 있다.

- 로그인 실패 횟수를 세지 않는다. 429는 테스트가 핸들러를 덮어써서 만든다.
- 목의 401 본문에는 `status` 필드가 들어 있다. 실제 서버의 본문에는 없을 수 있고, 그래도 화면은
  맞게 동작해야 한다 (2절 오류 본문).
- 목은 세션 쿠키에 `HttpOnly`를 붙이지 않고 `Secure`도 없다. 쿠키 이름(`codari_session`)과 값(사용자
  id)도 목이 임의로 정한 것이다. 실제 쿠키는 위 ②를 따른다.
- 비밀번호 불일치와 가입되지 않은 이메일을 목이 구분하지 않는 것은 맞지만, 그것은 목이 계정 목록에서
  이메일·비밀번호 쌍을 찾는 방식이어서일 뿐이다. 실제 서버가 ①을 지키는지는 목으로 알 수 없다.

## 7. 팀이 정할 열린 질문

이 문서가 정하지 않고 팀에 넘기는 질문이다. 두 읽기가 있다.

**읽기 1 — 로그인 폼도 비밀번호 규칙을 검사한다.** `docs/feature-spec.md`의 '계정 규칙' 절 제목은
`(COM-02·06·07·08 공통)`이어서 COM-07(이메일 로그인)을 그 규칙이 적용되는 기능으로 올려 둔다. 문서 그대로
읽으면 로그인 폼이 비밀번호 길이·문자 규칙을 검사하는 것이 자연스러운 해석이다.

**읽기 2 — 로그인 폼은 검사하지 않는다.** 지금 프론트가 택한 쪽이다
(`web/src/features/auth/loginSchema.ts`는 이메일 형식과 빈 값만 본다). 이유는 두 가지다.

- 나중에 규칙이 바뀌면, 바뀌기 전에 가입한 계정은 자기 비밀번호를 입력조차 할 수 없게 될 수 있다. 가입 화면(COM-06)은 이 PR의 범위 밖이라
  아직 없다. 지금 겪는 문제가 아니라, 규칙을 강화한 뒤 그 이전에 만든 계정이 새 규칙에 걸릴 때의 위험이다.
- 길이 때문에 거부하면 그 자체가 실패 이유를 구분해 주는 것이어서, 이유를 구분하지 않는다는 COM-07 본문과
  어긋날 수 있다.

어느 쪽이 맞는지는 이 문서가 정하지 않는다. 팀이 정해 주길 바란다. 규칙의 값은 이 문서에 옮겨 적지 않는다.
한 곳(`docs/feature-spec.md`의 '계정 규칙')에만 둔다.

## 8. 이 문서에 없는 것

회원가입(COM-06), 비밀번호 재설정(COM-08), 이메일 인증번호 발송은 이 화면(#20)의 범위가 아니라 다루지
않는다. 계정·비밀번호·인증번호 규칙의 값은 `docs/feature-spec.md`의 '계정 규칙'을 본다.
